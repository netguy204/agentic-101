# Session 3 — Anatomy of a delegation

<!-- Chunk: docs/chunks/platform_session_03_draft - The student's index for Session 3, written from its README and PREWORK -->

This is the session built on the delegation that went badly. Session 2
proved you can hand an agent work and read what it actually did; this one
takes the one that went worst, works out *why* it went worst, and teaches
you to write down what an agent needs so that it doesn't happen again.

A delegation stops being a sentence in this session and becomes a
structure — four things, on one page, for one task of your own.

**By the end you will have** written a one-page delegation brief for a task
from your own inventory — inputs, instruction, outputs, checkpoints — run
it, found the box that let you down, changed that one box for a reason you
can say in a sentence, run it again, and written down what your checks
would still miss.

## What it will cost you

| | |
|---|---|
| **The concept track** | About **25 minutes**. Four segments, listened to or read, with nothing to type. |
| **The lab** | About **110 minutes**, across several sittings. |

The lab figure includes the practice week. On your own there is no "between
sessions" to do practice in, so the laps that follow the main block are
simply the last sittings of the lab and are counted in the 110 minutes
rather than added on top. You will get the list of sittings when the lab
opens, each with its own honest number and the one thing you should have at
the end of it.

Two of those sittings run the brief on a real task, at whatever point in
the week that task next comes round — so this session's lab is spread out
by design rather than by slippage.

## What you will do

**In the concept track**, four things: why bad delegations go bad, and the
claim that there are only three ways it happens; the four things you owe a
capable colleague who cannot see your screen, does not know your company
and will not ask; the move to make when a run disappoints you — find the
box, change it once, run it again; and the question that decides whether a
task is one you should be delegating at all.

**In the lab**, four steps and then the practice laps. You take the
delegation from last week that went worst and sort what happened into one
of three reasons. You write a delegation brief for one task from your
inventory — four boxes, one page. Then the centre of the session: you run
it, read what came back, work out which of the four boxes let you down,
change that one box and write why, put the folder back to where it started,
and run it again. Last — and this is the part that is never skipped — you
name one thing that could go wrong that your checks would *not* catch, and
either add a check that would catch it or write **out** beside the task.

The practice laps that follow are the same brief on the real thing: one run
when the task next comes round, one more with a change between, and one
sentence about what the second run caught that the first didn't.

## Before you start

The prework is about 25 minutes: a piece of reading, one thing to finish,
one decision, and one command.

The thing to finish is your **worst delegation from Session 2's practice
week** — the what-did-it-do worksheet filled in on whichever of your
delegations went least well, including the question at the bottom about
what you would have failed to catch. If you did it, get it out. If you
didn't, it takes ten minutes now. Then write one sentence underneath it:
what you asked for, and what went wrong. Not an explanation and not a
defence — just what you asked and what happened. That sentence is the first
thing the lab uses.

> If all three of your delegations went well, use the one where the agent
> made a decision you hadn't asked it to make. There will be one. And if
> there genuinely isn't, "mine all went fine and I'm suspicious" is a
> perfectly good sentence to start from.

The decision is which entry from your toil inventory you will write the
brief for. A good one is marked *in*, passes Session 2's four questions —
you can check it, you're allowed to, it isn't a consequential decision, and
a person approves anything that leaves the folder — and has a file in it,
a list or a table or a set of records, something with rows for an agent to
grip. The entry your worst delegation came from is the natural choice if it
fits. Put a star next to it.

**If nothing on your sheet fits** — a thin inventory, or work that is all
confidential — there are ready-made briefs waiting for you in the lab, for
a character called Priya whose job has the same shapes in it as yours. They
take exactly the same time and produce exactly the same result, and one of
them is built to go wrong in a way that is worth meeting. Nothing about
this session needs your real data.

The command is `course-update`, in the course terminal. It fetches any
course fixes published since you set up — most weeks it says *Nothing to
do*. If it tells you to close the window and open a new one, do that. If it
says it couldn't reach the course updates, or anything else happens: stop
there and take what it printed to the course's TA. Don't try to fix it,
and don't lose an evening to it. Nothing in this session depends on it
having anything to say.

> **The lab uses invented material, and the agent still talks to a model
> provider.** What you type, and any file the agent reads, is sent to that
> provider so the model can respond. So your brief describes the *shape* of
> your work rather than its contents, and the file it runs on is one you
> ask the agent to make up. Nothing confidential goes in the folder.
> Everything happens in `course-practice`, with the same save-and-restore
> commands around it as in Session 2 — real recovery for ordinary file
> changes in that folder, and not a security boundary.

When you get to the practice laps and start using the real task, the same
four questions from Session 2's practice sheet decide whether it's allowed.
They haven't moved, and the lab has the full wording.

## What you submit

Four things, and each is a by-product of the lab rather than homework on
top of it.

1. **Your delegation brief**, filled in — the four boxes, box 5, and the
   sentence at the bottom naming which box let you down and what you
   changed. The sheet is printed from the lab's handouts; print two, because
   the second is for the practice week.
2. **The output of `revert --list`.** The save-and-restore commands are ones
   *you* type rather than tools the agent calls, so using them leaves no
   trace in the session log. What that listing shows — your two runs, and
   the move back to the starting line between them — is the evidence that
   the brief ran twice from the same place.
3. **Your session log.** pi keeps a record of every session as a file on
   your own machine, automatically; `pi -r` finds it afterwards. It holds
   the two runs themselves.
4. **Your worst-delegation worksheet from Session 2**, with the sentence
   under it and one of the three reasons written at the top. It is what the
   lab opens on.

Two of those are facts anyone can read off a file. The other two are where
you say, in your own words, which box let you down and what your checks
would still miss — and those two are what the session is actually for. A
brief that ran twice without a named change is somebody who has learned to
operate the loop, which is the means and not the end.

If your honest answer to the last box is **out** — that you can't think of
a check you could really do — write it. It is a result, not a shortfall,
and the final session treats it as the skill.

## What comes next

Session 4 takes it as given that you own a brief that has run twice and can
say why the second run was better, and asks what happens when the same
brief has to run every week — the same four boxes, repeated, with the
checkpoints put where they buy the most. Your brief, with both its
sentences on the bottom, is what opens it.
